==qdrant is a vector database==
indexing method: hierarchical navigable small world
## when to use qdrant?
in need of a vector database to store and retrieve vectors based on similarity

## core concepts
### collections
a named set of points among which you can search. 
- **a collection of points must share dimensionality** (*named vectors don't abide by this restriction*).
- the following similarity metrics are supported to measure closeness within vectors: ***dot product***, ***cosine similarity***, ***euclidean distance*** and ***manhattan distance***.

### points
what qdrant operates with. **a vector and optionally its payload .**

points are grouped in collections where they can be searched for and filtered through.

point can be modified async and in two steps: modification written to write-ahead-log (after this the op won't be lost even if machine loses power).

a simple point:```
``` python
{
    "id": 211, # supports 4-bit unsigned integers and uuid
    "vector": [0.1, 0.2, 0.3, 0.4],
    "payload": {"lang": "en(UK)"}
}
```

> to optimize performance qdrant supports batch uploading of points.
### vectors
central component of qdrant architecture.

supported types of vectors:
1. **sparse vectors:** no fixed length. few non zero elements. Useful for exact matches and collaborative filtering recommendations.
2. **dense vectors**: regular vectors, generated by the majority of embedding models.
3. **multivectors:** matrices of numbers with fixed length but variable height. Usually produced by models like colBERT.

each point in qdrant might hold 1 or more vectors. each point in qdrant can have several types of vectors attached (**named vectors**).
### payloads
metadata stored along side vectors to provide additional information.
can be used to filter during query search.

## search/retrieval process
for the retrieval process, qdrant uses dense vector (good for capturing process) but since they can sometimes miss specific technical terms or unique identifiers, qdrant also utilizes **sparse vectors** designed to capture precise **lexical matches** for specific keywords.

from a qdrant perspective, the process of generating vector embeddings using ML models is called inference. **Qdrant provides client side inference and cloud side inference.** Cloud side might be interesting if you already have an inference service set up on your end or you want to host your own model (ex.: fastembed).

search process using qdrant:
og. `query` → `vectorized(query)` → `similarity + topK` (K as results wanted by the user)

## how I used it
used in [[corporate_rag]] to store toy shipment docs as embeddings in a qdrant cloud collection.
queried qdrant through a langgraph `retrieve` node to pull context for the `generate` step (plain semantic search, no payload filtering).
